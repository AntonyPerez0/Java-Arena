# Java Arena libraries: JUnit 4 and a practice version of JavaFX

`build.mjs` packs the libraries a program may use on top of `java.base`, each as one archive of class files in `engine/dist/libraries/`, which both halves of the engine read:

- the compiler puts its classes on javac's class path for a program that uses it (`javac.loadLibrary` and the `libraries` option of `compile` in `engine/dist/compiler/javac-host.mjs`);
- the runner loads its classes next to the program's own, so the program really runs with them.

The site fetches an archive only when a program uses the library, and keeps it in the same cache as the rest of the engine. Which libraries a program uses is decided in one place, `librariesFor` in `src/grader/libraries.js`, for the browser's grader and free runs, the content build, its browser replay and the fidelity suite.

| Archive | What | Used when a source file mentions | Code |
|---|---|---|---|
| `junit4.bin` | JUnit 4.13.2 and Hamcrest Core 1.3 (the MOOC's part 6, unit testing) | `org.junit` | third-party, unchanged (below) |
| `javafx.bin` | Java Arena's practice version of JavaFX (the MOOC's part 13, graphical user interfaces) | `javafx.` | Java Arena's own (MIT, like the rest of the site) |

## Rebuild

```sh
node engine/libraries/build.mjs
```

It downloads the two JUnit jars from Maven Central (repo1.maven.org), or takes them from `node_modules/.cache/java-arena-libraries/`, checks their SHA-256, and keeps their class files. It compiles `javafx/src/` with the reference JDK's javac (Temurin 21.0.10+7, from `JAVA_HOME` or `scripts/get-jdk.sh`; the script stops on another version): `--release 21 -g`, with string concatenation compiled to `StringBuilder` calls (`-XDstringConcat=inline`), which the browser's interpreter runs faster than the `invokedynamic` form, and warnings as errors. Then it writes `junit4.bin` and `javafx.bin` (each a gzip stream of entries sorted by name, each `short nameLength, UTF-8 name, int dataLength, data`, with a fixed gzip header, so two runs give the same bytes), `manifest.json` (`files`: size, SHA-256 and class count of each archive; `sources`: the pinned jars; `own`: the library that is Java Arena's own code, with no third-party license) and the license texts that come inside the jars. javac writes the same class files for the same sources, so `javafx.bin` is byte-identical on every rebuild with the same JDK.

## Java Arena's practice version of JavaFX

Real JavaFX needs a native graphics toolkit and its own event thread: it doesn't run on Ristretto, Java Arena's runner, nor on the other browser Java engines that the research in [`docs/research/`](../../docs/research/) looked at (CheerpJ lists JavaFX as future work, and TeaVM's class library has no JavaFX). `javafx/src/` is our own small implementation of the part of JavaFX 21's API that the GUI lessons use, in JavaFX's own packages so learners write ordinary JavaFX code, written for this site (not OpenJFX's code; its behavior follows JavaFX 21, checked against OpenJFX 21.0.12 run headless with Monocle). Its internal code is in the package `arena.fx`, which isn't for learners.

A program that uses it runs to the end like any other. `Application.launch` starts a thread named `JavaFX-Launcher`, which starts the `JavaFX Application Thread`, makes the program's `Application` there and calls `init()` on its own thread; `start(primaryStage)` runs on the JavaFX Application Thread, then the events listed in `.arena/events.txt` (in the program's working folder; none when it's missing) are applied there one by one, each after the previous one's handlers and the `Platform.runLater` tasks they queued. The session ends after the last event, or when `Platform.exit()` is called or the last showing window closes; the windows are then written to `.arena/window.json`, the tasks still queued run, `stop()` runs, and `launch` returns. As the toolkit then exits, the tasks queued until then run too (those `stop()` queued, and those of a constructor, `init` or `start` that failed), and a task one of them queues is dropped, as in real JavaFX. Exceptions in the constructor, `init`, `start` and `stop` are reported as JavaFX reports them, and one that escapes an event handler, a task or a change listener goes to the thread's uncaught exception handler (which prints it) while the session goes on. Only for `npm run fx-check`, which sets the system property `arena.fx.stepWindows` on the reference JDK, the window after each event line (while the session goes on) is also written, as `.arena/window-step-N.json` for the N-th line, so the check can compare it with real JavaFX's; the site never sets it.

One class outside JavaFX's packages, `com.sun.javafx.iio.ImageStorageException` (an `IOException`), is there only so that an image that isn't an image reports the same exception as in JavaFX (`Image.getException()`).

The event list has one event per line (blank lines and lines starting with `//` are skipped): `click <target>`, `type <target> "text"` (one `appendText` per character, as typing does), `set <target> "text"` (one `setText`), `enter <target>` (a text field's `onAction`) and `close` (the main window's close button); for part 14, `set <slider> 25` (the slider's thumb let go at 25: kept between its ends, snapped to the nearest tick when it snaps, then set once, as `Slider.adjustValue` does), and the mouse on a canvas or an image view: `press <target> at x y`, `drag <target> to x y`, `release <target> at x y` and `click <target> at x y` (a press, the `Platform.runLater` tasks it queued, then a release). Numbers are written as digits, with a minus sign and a decimal point if needed. The mouse events come in JavaFX's order, as one-off runs on OpenJFX 21.0.12 with its Robot showed while the library was written (`npm run fx-check` can't re-run them yet: its driver doesn't fire mouse events): a release fires `MOUSE_RELEASED`, then `MOUSE_CLICKED` when it is on the node where the mouse was pressed (also after a drag, as in JavaFX, whose click needs only the press and the release on the same node) and its handler didn't throw; a release away from where the mouse is drags it there first; a drag to where the mouse already is fires nothing. A target is `#N` (the node numbered N in the window JSON of the moment), `#id`, `Type "text"` or `Type K` (the first node of that class, or of a class extending it, with that text, or the K-th, counted in outline order). An event that can't happen is skipped with a problem in plain English in the window JSON, such as `click Button "Add": there's no button with the text "Add"`. The format of the window JSON is described at the top of `javafx/src/arena/fx/WindowJson.java`.

For part 14.3 (a game), four more lines: `press key LEFT` (a `KEY_PRESSED`), `release key LEFT` (a `KEY_RELEASED`), `key SPACE` (a press, the `Platform.runLater` tasks it queued, then a release) and `frames 30` (30 frames of the game loop, at most 3600 in a line). A key is named as `KeyCode` names it (`LEFT`, `UP`, `SPACE`, `A`, `DIGIT1`); a wrong name is a problem naming the closest real one (`key ESC: there's no key called ESC (did you mean ESCAPE? ...)`, and `press key left` says to write it in capital letters). Pressing a key that is held, or releasing one that isn't, is a problem too. When the session ends between the press and the release of `key` (`Platform.exit()` in the press handler or a task it queued, or the last window closed), no `KEY_RELEASED` comes, as on real JavaFX; a window closed while another still shows doesn't end it, and the release still goes to that scene. Key events go to the scene of the window shown last that still shows (the library's rule: a desktop gives the focus to the window its window manager focuses, and fx-check uses the same rule, so this choice isn't checked against real JavaFX), to its `setOnKeyPressed`, `setOnKeyReleased` and `setOnKeyTyped` handlers: no node has the focus here (`requestFocus()` gives it to no node), so a node's own key handlers are stored but never run (the window JSON marks them, as the mouse handlers of other nodes). `requestFocus()` remembers the node: when that node, or a pane around it, has its own handler for a key event that a key line fires, real JavaFX would run it first, so the line gets a problem saying so (`key RIGHT: the program called requestFocus() on a node with its own setOnKeyPressed, which real JavaFX would run first; ...`), once per kind of key event in a session. As on OpenJFX 21.0.12 (its headless platform, a US keyboard, Shift up; checked with its Robot), a key that makes a character (the letters, the digits, Space, Enter, Tab and the punctuation keys) has it as its text on `KEY_PRESSED` and `KEY_RELEASED` (`"a"` for `A`, a line feed for `ENTER`), and its `KEY_TYPED` (with the character, the code `UNDEFINED` and no text) comes right after its `KEY_PRESSED`; other keys (the arrows, Shift, Escape, the keypad's digits) have the text `""` and no `KEY_TYPED`. These texts follow the headless platform; a desktop can differ for Enter and the punctuation keys (Enter's text and character are usually `"\r"` there, and the `[` and `]` keys come as `OPEN_BRACKET` and `CLOSE_BRACKET` with the texts `"["` and `"]"`, where the headless platform gives those to `BRACELEFT` and `BRACERIGHT`), so lessons don't print them (content/README.md). Letters, digits, Space and the arrows are the same everywhere. A held key doesn't repeat its `KEY_PRESSED` (on a real computer the system repeats it about 30 times a second while the key is held; a game that keeps the keys held in a map, as the MOOC's does, behaves the same). In a frame every `AnimationTimer` that was started when the frame began has its `handle(now)` called, in the order the timers were started, even one an earlier timer stopped in that frame; a timer started during a frame runs from the next one, and starting a started timer changes nothing (as OpenJFX 21.0.12 runs its timers from its pulses). `now` is a made-up clock: frame k of the session (from 1) gets 1,000,000,000 + k × 16,666,667 ns (real JavaFX's comes from the computer's clock: lessons never print it). After the timers the frame is recorded for the page's animation, then the tasks queued meanwhile run; frames stop when the session ends (`Platform.exit()` in a `handle`). The window JSON keeps the first 3600 frames (each node's first frame with what isn't its default, then only what changed, numbers in hundredths) and the count of all of them; the outline adds one line, `frames run: 120`, when any ran.

**Shapes and their geometry.** Nodes have `setTranslateX`, `setTranslateY`, `setLayoutX`, `setLayoutY` and `setRotate` (degrees, clockwise on the screen, about the center of the node's own bounds), and `getBoundsInLocal()` and `getBoundsInParent()`. For shapes these are JavaFX's own, worked out as OpenJFX 21.0.12 works them out, in float precision (checked against it on 1,500 random shapes, each turned, moved and stroked at random): exactly the same for polygons without a stroke, rectangles, lines and circles that aren't turned (or are turned by a multiple of 90 degrees). A stroked polygon's bounds are the outline of its stroke (miter joins) and 0.5 more, as JavaFX gives them, but JavaFX's stroker works in float and can differ in the last digits (up to about 0.1 at a very sharp corner); a circle turned by another angle keeps the box of its center and radius, where JavaFX's are, for some angles, those of the curves it draws a circle with (up to 0.03% of the radius bigger). A shape with neither a fill nor a stroke (`setFill(null)` on a polygon, a line with `setStroke(null)`) covers nothing, and its bounds are empty, as JavaFX's (found by fx-check's probe 29), except its bounds in parent after a turn by an exact quarter (90, 180 or 270 degrees): JavaFX then turns its empty bounds as if they were a box from (-1, -1) to (0, 0) and gives a box of 1 x 1 there, moved by the translate and layout, and so does Java Arena (probe 31). A `Text`'s bounds are an estimate (Java Arena doesn't measure fonts: 0.93 of the size above the baseline, 0.24 below, half the size wide per character); a pane's are its preferred size (or 0) with its children's bounds, a canvas's its size, a control's 0 by 0 (no layout, as before). `Shape.intersect(a, b)` (see `javafx/src/arena/fx/Overlap.java` and `Polygons.java`) works out the area the two shapes share, each with its fill (when it has one) and its stroke (when it has one), placed in its parent's coordinates, a circle as JavaFX's four cubic curves: shapes that only touch, along an edge or at a corner, don't overlap, and the result's `getBoundsInLocal()` is JavaFX's empty bounds (width and height -1). Whether two shapes overlap is meant to match OpenJFX 21.0.12 for every shape with area: it matched in 28,000 random cases (polygons convex or not, circles, rectangles, lines and strokes, turned, moved and laid out, 16,000 of them made to touch or to overlap by 1e-7 to 1), but later random cases found stroke overlaps on whole-number coordinates where they differ (a small overlap of a stroke can be missed), and a stroked polygon whose points are all on one line has area only through its stroke and can differ too (see also "Shapes without area" in scripts/fx-check/README.md for a polygon with no area of its own, turned); the box of the shared area matched exactly for polygons and rectangles without a stroke, but in 5 of those cases: in 4 JavaFX's crossing point came out 1e-17 to 1e-12 beside the whole number where Java Arena's is (such as -3.2E-15 for 0), and one was a polygon that crosses itself and goes back along an edge, where OpenJFX's box is bigger than the area the polygon fills (Java Arena's is that of the filled area, checked by sampling it); the box of a result with a circle or a stroke in it is only approximate: it can be smaller than JavaFX's by a good part of the radius (the arcs away from the other shape are kept as one chord per quarter, up to about 0.29 of the radius inside the curve), and differ by tenths of a pixel or more for strokes. So only empty or not is meant to match for circles and strokes, and a lesson never prints those boxes. A `Text` takes part as its estimated box, and a `Path` from an earlier `intersect` as its box. A scene made without a size whose root pane has a preferred size (`setPrefSize(600, 400)`) takes that size when its window shows, as in JavaFX. `Point2D` uses JavaFX's formulas (the same digits, checked on 400 values), `BoundingBox` its `contains`, `intersects`, `equals`, `hashCode` and `toString`, and the shapes' `toString` JavaFX's form (a `Path` from `intersect` has no elements: it knows only its box).

**Speed.** The browser engine interprets bytecode, where a method call costs about a microsecond and `Math.sqrt` and `Math.sin` tens of them, so the game's parts are made for it: a shape keeps its outline, transform and bounds until a setter changes it (`NodeData`, counted by `Frames.touch`), `intersect` first compares the circles around the two shapes (no square root) and places their outlines only when those meet, convex outlines are compared with a quicker test, and a frame records only the nodes that changed, writing its numbers into a character array. In headless Chromium on this 4-core machine (October 2026), a game of 20 turning, moving and wrapping polygons, a turning ship and 3 shots, with 80 `intersect` calls a frame, took 2.7 to 2.9 s for 300 frames (warm; 3.1 to 3.3 s for the first run in a new page) and 4.7 to 5.1 s for 600, with a window JSON of 274 KB and 543 KB (the first version of the library took 20 s for the 300 frames: most of it the square roots and sines of every shape's outline placed again for each `intersect`). Of a warm run of 300 frames, about 0.7 s is starting the program and JavaFX, 0.5 s recording the frames and 0.1 s writing the window; the rest is the game's own code with its 24,000 `intersect` calls (about 17 microseconds each when the shapes are far apart).

Where Java Arena's version differs from JavaFX on purpose (part 14): the mouse events go to the node the event line names, and only to a canvas or an image view, whose size it knows (a press must be on it, inside the canvas or on a pixel of the image that isn't fully transparent, as JavaFX picks an image view), not to the panes it is in, and `getSceneX()` and `getSceneY()` are the same as `getX()` and `getY()`; a canvas records its drawing calls (the first 5000, with the state each used, a text's font with its style when it isn't Regular: each one costs time in the browser engine when the window is written) and the page draws them, so its pixels can't be read; an image is read only from a PNG file (`file:name.png`, in the program's folder; JavaFX also reads JPEG, GIF and BMP, and other addresses; a `file:` address naming another computer, which JavaFX tries by FTP, gives an error image with an `UnknownHostException`, as JavaFX does for a name that doesn't exist, while for one that does JavaFX gives a connection error), and an address without a scheme is, as in JavaFX, a class path resource, which a program's folder never has here; charts aren't laid out, so an auto-ranging `NumberAxis` keeps the bounds it has (the page works out the range it draws), while an auto-ranging `CategoryAxis` takes the data's categories when its window shows and after each event, in the order they first appear in the data (that matches JavaFX right after `show()`, when the data didn't change after its series went into the chart; after a change, JavaFX keeps the earlier order and puts new categories after it, keeps the category of a removed point, and fills a line chart's only in a later layout pulse, and a bar chart fills its categories as data is added, also before `show()`), and a `null` value in a chart's data fails then, as JavaFX's layout does (`show()` throws, or later the exception goes to the uncaught exception handler once); `MouseEvent.toString()` leaves out JavaFX's pick result. A mouse handler set on another node (a button, a label, a pane) compiles, as in JavaFX, but never runs, since no mouse event goes to it: the window JSON says which nodes have one, and the page says the handler never runs here. Everything else of these classes a program can observe is meant to match JavaFX 21, as `npm run fx-check` checks on OpenJFX 21.0.12 (its probes 23 to 28): colors bit for bit, PNG pixels of every kind (with the rounding of JavaFX's premultiplied alpha, and JavaFX's way of reading chunks in an unusual order or of an unusual length), errors and their messages; JavaFX's PNG loader also logs warnings about such chunks (a `PLTE` in a gray image, a second `PLTE`, a `tRNS` before `PLTE`, no image data), which Java Arena's doesn't print. And as in part 13, it doesn't lay windows out, so a scene's size is the one given to its constructor (else 0) and a window's width and height are what `setWidth` and `setHeight` recorded (else NaN); it has no style sheets, so `setStyle` is stored but not applied (real JavaFX applies it, and its own style sheet gives controls padding when they show); fonts aren't looked up on a computer, so `Font.font("Arial", 20)` keeps the family Arial (real JavaFX gives the System font when Arial isn't installed), while JavaFX's own families (System, Serif, SansSerif, Monospaced, with their aliases) follow JavaFX's rules exactly; and it makes controls and scenes before `launch` (in a static field or in `main`), as real JavaFX does only when its toolkit started before `main`. That is how the JDK's launcher starts an `Application` main class from the module path (`java --module-path ... --add-modules javafx.controls Main`). With JavaFX on the class path and `main` called directly (Maven's exec:java, a separate launcher class, fx-check's driver), or a main class that isn't the `Application`, real JavaFX starts its toolkit in `launch`, so `new Label(...)` before it fails with ExceptionInInitializerError (Toolkit not initialized) and `new Scene(...)` with a NullPointerException. The lessons make them in `start`. Everything else a program can observe is meant to match JavaFX 21: `scripts/javafx.test.mjs` tests it on the reference JDK, fidelity program 48 checks that the browser engine gives the same bytes, and `npm run fx-check` ([`scripts/fx-check/`](../../scripts/fx-check/)) runs the lessons' JavaFX programs, the fidelity programs and probes of the whole API on real OpenJFX 21 without a screen and compares the output and the windows, a canvas's drawing as pixels (its recorded calls drawn again on real JavaFX).

On the reference JDK, a program whose main class extends `javafx.application.Application` runs through `scripts/javafx/JavaFxLauncher.java` (see there): the JDK's own launcher refuses such a class when JavaFX isn't one of its modules, while the browser engine just calls `main`.
