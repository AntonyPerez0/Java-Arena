# The real-JavaFX check

Java Arena runs its own practice version of JavaFX (`engine/libraries/javafx/`), because real JavaFX doesn't run on Java Arena's engine (Ristretto) or on the other browser Java engines that the research in [`docs/research/`](../../docs/research/) looked at. The lessons say that the same code runs with real JavaFX on a learner's own computer, and that a check on every model solution confirms it shows the same window contents there. This folder is that check.

```sh
npm run content     # (or npm run build) lists the lesson programs in fidelity/out/content-checks.json
npm run fx-check
```

On a 4-core machine the probes and the fidelity programs (65 runs, each on both sides) take about 40 to 60 seconds, and each lesson run adds well under a second (four programs run at a time): with the 465 runs of the lessons and drills of October 2026 (with the games of module 53), about 4 to 5 minutes in all (4 minutes 18 seconds on October 11, with other work on the machine, comparing 1,074 windows after earlier event lines besides the 526 at the end; `FX_CHECK_CANVAS_SELFTEST=1` adds a few seconds). The first run also downloads the jars (about 8 MB). CI runs it on every pull request after the site is built, and fails on any difference. The summary is also written to `fidelity/out/fx-check.json` (kept as a CI artifact).

## What it does

The programs are every program that uses JavaFX (a source file mentions `javafx.`) among:

- **the lessons and drills**: every program the content build ran that uses JavaFX, read from `fidelity/out/content-checks.json` (each challenge's model solution with every test's input, arguments, files and clicks and typing, each `java window` example with its events block, and any `java run` example that uses JavaFX). The check warns when a lesson file is newer than that list.
- **the fidelity programs** that use JavaFX (`fidelity/programs/48-javafx-window`, `49-javafx-charts-images`, `50-javafx-limits` and `51-javafx-game`, with their `.arena/events.txt`).
- **the probes** in `probes/`: our own programs that go through every class and method of the API of parts 13 and 14 (below).

For each, it compiles the program twice with the reference JDK's javac (Temurin 21.0.10+7, in one JVM as the content build does): against Java Arena's JavaFX (`engine/dist/libraries/javafx.bin`) and against the real jars. Then it runs it both ways, each in a fresh folder holding the same files (an image of `content/assets` that a test or an example gives, as its bytes), with the same standard input and arguments and the reference JVM flags:

- **Java Arena's JavaFX** on the reference JDK, exactly as the content build runs it (through `scripts/javafx/JavaFxLauncher.java`), with the events in `.arena/events.txt`. The library writes `.arena/window.json`.
- **Real OpenJFX 21** on the reference JDK, without a screen (Monocle's headless platform, software rendering), through `RealFxDriver.java`, our own driver. (Monocle's headless screen is made 4096 x 4096 pixels: on its own 1280 x 800 screen, a window bigger than the screen makes the renderer fail with a `BufferOverflowException` as it paints the window, as fidelity program 50's does.) The driver runs the program's `main` on the main thread, waits until `start` has returned, then applies the same events with the real API on the JavaFX Application Thread, each after the `Platform.runLater` tasks queued before it have run, as the library does: `click` calls `fire()`, `type` calls `appendText` once per character, `set` calls `setText`, `enter` fires an `ActionEvent` at the text field (what pressing Enter does), `close` closes the primary stage, `set Slider N value` calls the real `Slider.adjustValue(value)` (what letting the thumb go there does: kept between min and max, snapped to the ticks when the slider snaps, set once), the mouse events are real mouse events, the key events real key events and `frames` runs the game loop frame by frame (below). Before the first event and after each one it lays out every showing window (`layout()` on each root; what that throws goes to the uncaught exception handler, as in a pulse), as JavaFX's next pulse would, so what a program sees after an event doesn't depend on when the pulse comes. Targets (`#N`, `#id`, `Type "text"`, `Type K`) are found in the same outline order and give the same problems in the same words. Then it writes the windows from the real scene graph as the same window JSON (part 14's nodes as below) and calls `Platform.exit()`, so `stop()` runs and `launch` returns, as with the library. When the session ends earlier (`Platform.exit()`, or the last window closed), the JSON says the windows were closed; when the constructor, `init` or `start` fails, there is no window file, as with the library.

**The mouse.** `press`, `drag`, `release` and `click ... at x y` are real `MouseEvent`s made with JavaFX's own constructor, at the point turned into the scene's coordinates (`localToScene`), and handed to the scene as the toolkit hands it a mouse event (`Scene.processMouseEvent`, the method the toolkit calls). So real JavaFX itself picks the node under the point (an image view only where its pixel isn't transparent), sends the drags and the release to the node the mouse was pressed on, and decides whether a `MOUSE_CLICKED` follows a release, and the handlers get the coordinates JavaFX computes. The driver does only what a mouse does: no drag when the point didn't change, a drag to the release's point first when the release is somewhere else, and for `click ... at` a press, then (after the tasks the press queued) a release at the same point. The checks of the event lines (a point off the canvas or on a transparent pixel, a mouse that isn't pressed, a hidden or disabled node) give the same problems in the same words as the library's, using the real node's `contains`.

**The keyboard.** `press key`, `release key` and `key` are real `KeyEvent`s made with JavaFX's own constructor and handed to the scene as the toolkit hands it a key event (`Scene.processKeyEvent`), so real JavaFX sends each to the focus owner when there is one, else to the scene: `KEY_PRESSED`, then `KEY_TYPED` for a key that makes a character, and for `key` the `KEY_RELEASED` after the tasks the press queued. They go to the window shown last that still shows, chosen by the library's rule on both sides (see "What it doesn't prove"). Once the session has ended between the press and the release of `key` (`Platform.exit()`, or no window shows any more), no `KEY_RELEASED` comes, on both sides; a window closed while another still shows doesn't end it, and the release still goes to the closed window's scene. The driver gives each key the text the library gives it (that of OpenJFX's headless platform, which the library's author checked with its Robot), so this checks where the events go and in what order, not the texts themselves. The checks of the key lines (a key already held, one that isn't held) give the same problems in the same words, and so does the library's problem for a `requestFocus()` on a node with its own key handler (here: the scene's real focus owner).

**The game loop.** Real JavaFX runs `AnimationTimer`s from its pulses, with real time. The driver pauses the toolkit's primary timer as soon as the toolkit is up (and again, on the JavaFX Application Thread, when a window shows, before `start` returns), with JavaFX's own `AbstractPrimaryTimer.pause()`: its main loop then skips the animation step of every pulse, so no timer runs by itself, while the scene's own pulses (CSS, layout, drawing) go on. A `frames N` line then runs N frames itself: in each, it reads the timers started at that moment from the primary timer's own list (`animationTimers`, the first `animationTimersLength`, in the order they were started: `start()` appends, `stop()` removes) by reflection and calls each one's `handle(now)` through its `TimerReceiver`, as a pulse does, with the library's made-up `now` (frame k gets 1,000,000,000 + k × 16,666,667 ns); then the tasks the frame queued run and the windows are laid out, before the next frame. A `handle` that throws goes to the uncaught exception handler, and the timers after it skip that frame, as in real JavaFX (the primary timer's own `timePulseImpl` loops over the timers with only a `try`/`finally`) and in the library; the next frame runs them all again. (The driver doesn't call `timePulseImpl` itself, since that would also step the toolkit's own animations with the made-up time.) One difference is left: in real JavaFX that exception also leaves the toolkit's pulse, so that pulse's CSS, layout and drawing are skipped too, while the library and the driver still lay the windows out after a frame that failed; it shows only if a later handler in the same `frames` line reads a size that depends on layout. The window JSON gives the count of frames run (`frames run: N` in the outline). The window after each `frames` line is compared, as after every event line (below); the frames inside one `frames` line, which the library records for the page's animation, are compared only through what the program prints in them.

This works on the real toolkit as it is: `Toolkit.getToolkit().getPrimaryTimer()` is JavaFX's own primary timer (an `AbstractPrimaryTimer`), whose public `pause()` the driver calls, and whose private fields `animationTimers` (an array of `TimerReceiver`) and `animationTimersLength` are read with reflection (the jars are on the class path, so no module flags are needed); a real `AnimationTimer.start()` adds its receiver to that array and `stop()` takes it out, so the array is the started timers in start order. Probes 29 and 34 check it: the order of timers started, started twice, stopped and started again inside `handle`, started from a key handler or a task, and a timer stopped by one that runs before it in the same frame (it still runs in that frame on both sides: a frame calls the timers that were started when it began, as a pulse does).

**After every event line.** Besides the window at the end, the check compares the window after each event line before the last: the outline and the events that couldn't happen so far. Java Arena's JavaFX runs with the system property `arena.fx.stepWindows` (which only the check sets), and then also writes `.arena/window-step-N.json` after the N-th event line (blank lines and comments don't count), after the tasks the line queued and the layout, while the session goes on; the driver writes the same, from the real scene graph, at the same point (`<window file>.step-N`). The check reports the first line after which the windows differ (later ones usually follow from it), or a session that goes on with one side only. A canvas's drawing is compared as pixels only at the end; after an earlier line, its place and size are. The summary says how many windows after an earlier event line were compared.

It reports, per run, every difference in:

- the **output** (stdout), exactly (identity hash codes such as `Label@1b6d3586` are masked);
- **stderr** without stack frames (the frames of JavaFX's internals and of the driver differ) and without what JavaFX logs about itself (its warning that it runs from the class path, its PNG loader's warnings about a file's chunks, which Java Arena's JavaFX doesn't print, fontconfig's warnings);
- the **exit code**;
- the **files** the program left in its folder (not Java Arena's own `.arena/`): text as it is, and a file that isn't UTF-8 text (an image it was given or wrote) by its size and the SHA-256 of its bytes, never as text;
- whether a **window file** was written, the **window outline** (`windowOutline` from `src/grader/window.ts`, the same function grading uses; lines that differ are marked), and the **events that couldn't happen** with their messages, at the end and after every event line before it (above);
- each **canvas's drawing**, as pixels (below).

What the outline compares for part 14's nodes, read from the real ones:

- **Charts**: the chart's class, title, legend and symbols (`setCreateSymbols`), each axis's class and label and, when it isn't auto-ranging, its bounds and tick unit, and every series (its name) with every data point (each value as the program gave it: a number, a text or null). The categories an auto-ranging axis takes from the data, and the bounds real JavaFX lays out for an auto-ranging `NumberAxis`, aren't in the outline (see below); what a program prints about them is compared as output.
- **Sliders**: min, max and value, tick labels, tick marks, the major tick unit and snapping, after the same `set Slider` events. (The minor tick count and block increment are in the JSON, not the outline.)
- **Image views**: the image's size and the CRC-32 of its pixels read through the real `PixelReader` (`getArgb`, row by row), so every pixel is compared; an image view without an image, or with an error image and its exception's message.
- **Canvases**: the canvas's place and size in the outline; its drawing as pixels, as follows.
- **Shapes and moves** (part 14.3): `Polygon`'s points, `Circle`'s center and radius, `Rectangle`'s place and size, `Line`'s ends, `Text`'s text, place and font, a `Path`'s box (`getBoundsInLocal()`, from `Shape.intersect`), each shape's fill, stroke and stroke width (a value JavaFX's own style sheet gave counts as not set), every node's translate and rotate, the scene's key handlers and the count of frames run. A node's layout (`layoutX`, `layoutY`) is compared only for a window's root and the children of a plain `Pane` (the class `Pane`, or a program's class that extends it), which never moves its children: real `VBox`, `HBox`, `StackPane`, `BorderPane`, `GridPane` and `FlowPane` set their children's layout when they lay them out, which the library, without layout, doesn't do.

**Canvases.** Real JavaFX doesn't tell what was drawn on a canvas, so the driver takes a snapshot of each real canvas (`Canvas.snapshot` on a transparent background, on the JavaFX Application Thread, after the events), and `CanvasReplay.java` draws the calls Java Arena's JavaFX recorded for it (each with the paint, line width and font it used) again on a new canvas of real JavaFX of the same size, and takes its snapshot. Every pixel of the two must be within 2 of 255 in opacity and in each premultiplied color (`canvas.mjs`): the recorded colors are rounded to 8 bits per channel (`#rrggbbaa`), so a color a program made from doubles can blend a step or two away; otherwise the pixels are the same. When they differ, the check says how many pixels differ and where; `FX_CHECK_SAVE=<folder>` saves both drawings as PNGs to look at. A canvas with more calls than Java Arena keeps (5000) can't be drawn again, so its drawing isn't compared (the summary lists it; its place and size are). This proves that the recording holds what the program drew, in order and with the state each call used, as real JavaFX draws it; it doesn't check how the page draws the recorded calls in the browser (approximately: see content/README.md).

How well it tells right from wrong (October 2026; `FX_CHECK_CANVAS_SELFTEST=1` runs it again on every canvas the check compares): for each canvas, deliberately wrong versions of its recorded calls (each call moved by 1 and by 0.5 pixel, one size 1 bigger, a polygon's point moved, its color off by 8 and by 32 of 255, its line width off by 1 and by 0.5, the call left out, a rectangle drawn as an oval and the other way round, a text one letter different, one point bigger or in another family, the last two calls swapped) were drawn on real JavaFX and compared with the real canvas. Over the 31 canvases of the probes, the fidelity programs and the lessons and drills (the run of October 11, 2026), all 31 right drawings passed, and of 1078 wrong ones, 73 drew exactly the same pixels as the right one (a change hidden under a later call, or outside the canvas, which no comparison of what the canvas shows can see) and all but 2 of the other 1005 failed. The 2 that passed differ from the right drawing by at most 2 of 255 in a few edge pixels: an oval moved by half a pixel under a thicker outline drawn on it, and two lines of the same color, meeting at a point, drawn in the other order.

The comparison was first tried as the design suggested, drawing the recorded calls with java.awt (anti-aliased, the same stroke caps and joins) instead of on real JavaFX. Shapes came out the same to within 4 of 255 in every pixel, but texts didn't: JavaFX draws `fillText` with its own glyph rasterizer, and java.awt's glyphs differed at their edges (the pixels of a text's box differed by 4 to 10 on average), so a text one letter different (10.6) couldn't be told from a right one (up to 10.1). Drawing the calls again on real JavaFX has none of that, so the check uses it.

The events are read on the Node side with `parseEventLine` from `src/grader/window.ts` (which reads them as the library does, with the library's own messages for lines it can't read) and handed to the driver.

## The real jars

`jars.json` pins OpenJFX 21.0.12 (`javafx-base`, `javafx-graphics`, `javafx-controls`, Linux jars, the newest 21.0.x) and Monocle 21.0.2 (`org.testfx:openjfx-monocle`), each with its SHA-256. They are downloaded with curl from Maven Central (repo1.maven.org), or from Google's mirror of Maven Central when Maven Central refuses (it answers 429 to an address that asks too often), and kept in `node_modules/.cache/java-arena-fx/` (`FX_CHECK_CACHE` sets another folder), with JavaFX's native libraries unpacked next to them. A jar whose SHA-256 isn't the pinned one is never used. CI caches the folder with a key made from `jars.json`. The jars are only downloaded for this check: nothing of OpenJFX is in the repository or on the site. To move to a newer 21.0.x, change `jars.json` (versions, paths and SHA-256) and run the check.

Real JavaFX's text needs the system's fontconfig and pango libraries (any desktop Linux, and CI's Ubuntu, have them).

## Options

| Variable | What it does |
|---|---|
| `FX_CHECK_ONLY=<regular expression>` | Checks only the programs whose place matches, such as `probes/02` or `gui-basics` |
| `FX_CHECK_VERBOSE=1` | Also prints what each run printed on real JavaFX and its window outline |
| `FX_CHECK_CHECKS=<file>` | Reads the lesson programs from another file than `fidelity/out/content-checks.json` |
| `FX_CHECK_CACHE=<folder>` | Keeps the jars in another folder |
| `FX_CHECK_SAVE=<folder>` | Saves each canvas compared as two PNGs (`c<N>-real.png`, the real canvas, and `c<N>-ours.png`, its recorded calls drawn again on real JavaFX) and its calls (`c<N>.json`) |
| `FX_CHECK_CANVAS_STATS=1` | Prints, for each canvas compared, how many pixels differ by more than the tolerance |
| `FX_CHECK_CANVAS_SELFTEST=1` | Also checks the canvas comparison with deliberately wrong drawings of every canvas compared (see "Canvases" above) |

## The probes

Each folder in `probes/` is a program (`Main.java`, and more files if it needs them). Each `<name>.events` file in it is one run with those events (the format of `.arena/events.txt`); a folder without one runs once with no events. `meta.json` can give `args` (and `mainClass`) and `files`, images of `content/assets` that each run gets in its folder (`{ "files": { "pic.png": { "asset": "tiny.png" } } }`, as in a lesson's test), `stdin.txt` the standard input. The probes print what they observe, so the output comparison checks behavior that the window doesn't show.

## What a pass proves

- Each lesson program, run on real JavaFX 21 with the same input, arguments, files, clicks, typing, slider moves and mouse events, prints the same output (and the same exceptions on stderr), ends with the same exit code, writes the same files and leaves windows with the same outline (the same windows in the same order, with the same titles, the same nodes of the same classes in the same nesting, the same texts, ids, fonts, spacing, gaps, padding, alignment, preferred sizes, styles and flags; the same charts with the same series and points, sliders with the same values, images with the same pixels) and canvases with the same drawings (to within 2 of 255 in each pixel) as on Java Arena's JavaFX. So a learner who copies a model solution or example to their own computer sees the same window contents, and the clicks and typing of the tests do the same there.
- The library's API (parts 13 and 14) behaves as real JavaFX's does in everything the probes print and show, including error messages, except what is listed below.
- For a game (part 14.3): the same key strokes and the same number of frames, run frame by frame on real JavaFX's own timers, give the same output (what the program prints from its handlers and timers, such as collisions and points) and leave the same shapes in the same places, turned the same way, as on Java Arena's JavaFX, after every event line (each `frames` line too) and at the end. This is what module 53 means by "compared with real JavaFX 21": fidelity program 51 and every lesson and drill game run so on every pull request. The frames inside one `frames` line are compared only through what the program prints in them.

## What it doesn't prove

- **Not the drawing.** The outline is the window's contents, not its look: the page draws it approximately, and real JavaFX lays it out with its own style sheet (modena), fonts and sizes. Sizes are left out of the outline on purpose (the library doesn't lay windows out). Charts are drawn by the page approximately (its own auto-ranged bounds, layout and colors); a canvas's recorded calls are compared with real JavaFX's pixels, but how the page draws those calls in the browser (an HTML canvas, with the browser's fonts) isn't checked here.
- **Not the browser.** This runs Java Arena's JavaFX on the reference JDK. That the browser engine gives the same bytes is what `npm run fidelity` (program 48) and `npm run content:browser` check.
- **Not real clicks on controls.** Clicks and typing are applied through the API (`fire()`, `appendText`, `setText`, an `ActionEvent`, `close()`, `adjustValue`), as the library applies them, not through a mouse and keyboard: a real click also moves focus and can be refused by a control covered by another one, which this doesn't model. Mouse events on a canvas or an image view do go through the scene's own mouse handling, but not through the platform's (no `MOUSE_MOVED`, `MOUSE_ENTERED` or drag-and-drop events, which the library doesn't have either).
- **Not which window gets the keys.** On both sides the keys go to the window shown last that still shows, which is the library's rule. Monocle's headless platform says every showing window has the focus, so it can't decide; real JavaFX on a desktop gives the focus to the window the window manager focuses. Only the routing inside a scene (the focus owner, then the scene) and the order of the events are real. Lessons use one window for keys.
- **Only what a program shows or prints.** A difference the probes and lessons never exercise isn't found. The probes cover the API list of the design; the lessons cover what they use.
- **Only Linux, headless, one JavaFX version.** OpenJFX 21.0.12 with Monocle and software rendering. Other platforms can differ in fonts (below).

## What can't match, and how the check deals with it

These are differences between real JavaFX and Java Arena's JavaFX that a program can show, and that the check reports when a lesson does them. Lessons avoid them (content/README.md's Windows section says how):

- **Fonts the computer may not have.** Real JavaFX gives the System font for a family that isn't installed; Java Arena's JavaFX keeps the family asked for (as on a computer that has it). JavaFX's own families (System, Serif, SansSerif, Monospaced, in any case, with the aliases Dialog, DialogInput, sans-serif and monospace) behave exactly as in real JavaFX on every computer. The check says so when a differing window uses another family.
- **Styles.** Real JavaFX applies `setStyle` (CSS) to a node and, for fonts, to everything in it; Java Arena's JavaFX stores the style and the page draws it approximately. A style that sets the font, padding, spacing, gaps, alignment, sizes, wrapping or visibility changes what real JavaFX's window holds, so the check reports it (and says so). Styles for colors and borders are fine. Values that JavaFX's own style sheet gives (a button's padding, for instance) count as not set, since the program didn't choose them.
- **After the window shows, real JavaFX lays it out.** A window's or scene's size, and a control's padding or font, read after `show()` are the laid-out values there (the library keeps the values that were set). A lesson shouldn't print them after the window shows.
- **A chart's auto-ranging axes.** Real JavaFX fills a `BarChart`'s categories as soon as data is added to a series in it (also before `show()`; Java Arena's JavaFX fills them when the window shows), keeps the category of a removed point and the earlier order after a change, and fills a `LineChart`'s only in a layout pulse; Java Arena's JavaFX takes the data's categories again after each event, in the order they first appear. Real JavaFX also lays out an auto-ranging `NumberAxis`'s bounds (`0.0` to `5.5`, where the library keeps `0.0` to `100.0`), and, before the window shows, adding data to the first of two series in a `BarChart` reports an `IndexOutOfBoundsException` (from `BarChart.dataItemAdded`) that the library doesn't. So a probe or lesson reads `getCategories()` only right after `show()`, and only when the data didn't change after its series went into the chart, never prints an auto-ranging `NumberAxis`'s bounds after the window shows, and doesn't add data to a series already in a `BarChart` before the window shows. (The driver's layout after each event makes the real side repeatable; it doesn't make the order of categories after a change match.)
- **Several categories added at once, one of them already there or `null`.** Real JavaFX's `CategoryAxis` removes a category it already has from inside its list's change listener, which, when the change added several categories (`addAll`, `setAll`, or `addAll` to the list given to the constructor), leaves a list and reports exceptions (`IllegalArgumentException: Duplicate category ; a already present`, `UnsupportedOperationException`) in an order that depends on the nested changes (`addAll("a", "b", "a")` to an empty axis leaves `[b, a]`). Java Arena's JavaFX keeps them all and reports one `IllegalArgumentException`. Adding one category it already has (`add`) behaves the same on both (probe 27). Lessons don't add categories twice.
- **Mouse handlers on other nodes, and scene coordinates.** In real JavaFX a mouse event also goes to the panes around the node (it bubbles up), and a real click on a button also runs its `setOnMouseClicked`; Java Arena's JavaFX sends mouse events only to the canvas or image view a line names (the page says so under the window), so a pane's mouse handler would run on real JavaFX only. `getSceneX()` and `getSceneY()` are the point in the scene's coordinates in real JavaFX, and the same as `getX()` and `getY()` in Java Arena's JavaFX, which doesn't lay windows out: they match only for a node at the scene's top left (as in probe 25). Lessons put mouse handlers only on a canvas or an image view and use `getX()` and `getY()`.
- **Key handlers on a focused node.** Real JavaFX sends a key event to the scene's focus owner first (a node the program called `requestFocus()` on, or a control JavaFX focuses by itself, such as a `Button` or a `TextField`), and from there it bubbles up through the panes to the scene; Java Arena's JavaFX sends key events only to the scene's handlers. A program whose focused node (or a pane around it) has its own key handler gets a problem line saying so on both sides, but its output differs. A focused `Button` also fires on Space and Enter in real JavaFX. Lessons put key handlers on the scene, and a game's window holds no controls.
- **Layout under layout panes.** A `setLayoutX` or `setLayoutY` on a child of a `VBox`, `HBox`, `StackPane`, `BorderPane`, `GridPane` or `FlowPane` is undone by real JavaFX's layout; the check doesn't compare it there (above). Lessons move nodes only in a plain `Pane`.
- **Bounds where JavaFX works with floats and curves.** Real JavaFX's bounds of a stroked polygon can differ from the library's in the last digits (the stroke's outline), and so can a circle's turned by an angle that isn't a multiple of 90 degrees (real JavaFX measures its curves, up to 0.03% of the radius bigger) and the box of an `intersect` result with a circle or a stroke in it. Whether `intersect` is empty matched for all of probe 32's 6,000 random pairs, but it isn't exact for every stroke: other random cases found strokes on whole-number coordinates where a small overlap of a stroke is missed, and a stroked polygon whose points are all on one line (area only through its stroke) can differ too (see also "Shapes without area" below). The box of a result with a circle in it can be smaller than JavaFX's by a good part of the radius, and with a stroke differ by tenths or more. So the probes print those bounds only as the README of the library says they match (unstroked polygons and rectangles at any angle, circles turned by quarter turns), and a lesson never prints them (content/README.md).
- **Shapes without area.** A `Line` of length 0 and a `Polygon` with fewer than two different points: real JavaFX gives them bounds of its own making (a line of length 0 with the default stroke is a box of 1.414 x 1.414 around its point, 2.366 x 2.366 when turned by 30 degrees; one point is empty without a stroke and a box of 2 x 2 with one), and a polygon whose points are all on one line, turned, is a sliver of float rounding that `intersect` can find to touch a shape. Java Arena's JavaFX gives such a line the box of its stroke and such a polygon the box of its point. Found by probes 31 and 32 while they were written, and left out of them: no lesson draws such shapes.
- **The source of a `KeyEvent` made with its constructor.** Its `toString()` names the event's source and target, which real JavaFX sets to a placeholder object of its own whose class name is a lambda's (`javafx.event.Event$$Lambda/0x...`, different in every run); Java Arena's JavaFX names a plain `Object`. Probe 33 prints the rest of it.
- **Images that aren't PNG.** Real JavaFX reads JPEG, GIF and BMP files; Java Arena's JavaFX gives an error image saying it reads only PNG images. Lessons use the PNGs of `content/assets`.
- **A canvas with more than 5000 drawing calls.** Java Arena keeps the first 5000 (and counts the rest), so the drawing can't be drawn again to compare; the check compares the rest of the window and lists the canvas as not compared (fidelity program 50 has one, on purpose).
- **A window shown without a scene.** Headless JavaFX fails in its next pulse (a NullPointerException in its renderer) and the session hangs, so the check can't confirm one. The library shows it as `(no scene)`.
- **`setFont(null)`.** Real JavaFX fails when it lays the control out; the library shows `font null`.
- **A task queued with `runLater` after `Platform.exit()`.** On real JavaFX it races with `stop()` (in 5 runs, `stop()` came first 4 times); the library runs it before `stop()`. A task queued before `exit()` runs before `stop()` on both.
- **A task queued by a task that `stop()` queued.** The task `stop()` queues runs on both, as the toolkit exits; one that task queues in turn races with the toolkit's exit on real JavaFX (it runs in some runs and not in others), and the library drops it. So a probe or lesson never prints from one.
- **A task queued with `runLater` in `init`, and what `init` does after that.** Real JavaFX runs the task on the JavaFX Application Thread as soon as that thread is free, while `init` goes on on the launcher thread, so a line `init` prints after queuing it races with the task's (in 20 runs of probe 09 alone, `init`'s line came first 19 times; with four programs running at a time, the task's came first in 9 of 80 runs of probes 05 and 09). The library runs the task after `init` returns, before `start` (or as the toolkit exits, when `init` failed or called `Platform.exit()`), so an `init` that waited for the task to run would never end there. So the probes print in `init` only before they queue a task, and a lesson never waits in `init` for one.
- **Controls made before `launch`.** Real JavaFX can make a control or a scene only after its toolkit has started, and when that happens depends on how the program is started. From the module path with an `Application` main class (`java --module-path ... --add-modules javafx.controls Main`), the JDK's launcher starts the toolkit before `main`, and the program behaves as on the library, which makes them at any time. With JavaFX on the class path and `main` called directly (as the driver runs programs), or a main class that isn't the `Application`, the toolkit starts in `launch`, so a control made earlier (a static field, or in `main`) fails with ExceptionInInitializerError (Toolkit not initialized). Lessons make them in `start`.

## Differences this check found and fixed in the library

When it was first run (October 2026), the probes found these, all now fixed in `engine/libraries/javafx/src` (and checked again by fidelity program 48 in the browser engine):

- `Font` didn't follow JavaFX's rules for its own families: `Font.font("Serif", 20)` was named `Serif` instead of `Serif Regular`; `Font.font("serif", 20)`, `"Dialog"`, `"DialogInput"`, `"sans-serif"` and `"monospace"` kept the name as written instead of becoming `Serif`, `SansSerif` and `Monospaced`; `new Font("Serif Bold", 18)` had the family `Serif Bold` instead of `Serif`, style `Bold`; and `new Font("Serif", 18)` (a family, not a full name) was Serif instead of the System font.
- `Platform.runLater(null)` threw at once; real JavaFX accepts it and the task fails with a NullPointerException when its turn comes.
- The children list's `add(index, node)` and `addAll(index, nodes)` checked the index after the nodes and with ArrayList's message; JavaFX checks it first (`Index 5 out of bounds for length 1`). `remove(from, to)` now gives JavaFX's message too (`Range [1, 0) out of bounds for length 2`).
- A program's threads made without a name were numbered from `Thread-0` after `launch`. JavaFX makes its launcher thread and (on Monocle) its application thread without a name and names them afterwards, so they take the next two numbers (a program's first thread made in `start` is `Thread-2`, not `Thread-0`); the library now makes its two threads the same way.

When the driver was extended to part 14 (October 2026), it found this, now fixed:

- A text drawn on a canvas in a bold or italic font (`new Font("Monospaced Bold", 12)`) was recorded with only the font's family and size, so the drawing lost its style: fidelity program 49's canvas differed from real JavaFX's in 41 pixels. The window JSON now gives a text's font `"style"` when it isn't Regular (`Font.getStyle()`, which JavaFX has, is now public in the library too), and the page draws the text in it; the outline still gives a font's family and size.

When the driver was extended to part 14.3 (keys, frames and shapes, October 2026), probe 29 found this, now fixed:

- A shape with neither a fill nor a stroke (`setFill(null)` on a `Rectangle`) had the box of its geometry as its bounds; JavaFX gives it empty bounds (width and height -1), since it covers nothing.
